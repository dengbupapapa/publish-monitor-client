# Design

## Context

列表页当前把过滤与分页全部折叠进路由 query，再由一个 `computed` 还原成 `state`：

```
route.query --(state computed)--> { matched, page, size }
                                        |
                                        v
                          watch([...]) --> load() --> GET /match-results
                                        |
                                        v
                        toListQuery(state) --> router.push/replace
```

三处现有实现决定了本次改动的形状（均在 `src/views/MatchResultList.vue`）：

- `state` 对每个键做白名单校验，非法值回落缺省，缺省值不回写地址。
- 规范化 `watch(route.query)` 只比对 `matched / page / size` 三个键，新增键若不加进去，地址会被反复改写或改不回去。
- `openDetail` 复用 `toListQuery(state.value)`，所以只要 `scope` 进了 `toListQuery`，从详情返回就自动恢复。

服务端侧 `scope` 已实现（`all` 默认 / `warn`），且 `warn` 与 `matched` 是按逻辑与叠加，`warn` + `matched=2` 恒为空集且不报错。动机见 `proposal.md`，行为契约见本次 `specs/match-result-list/spec.md`。

## Goals / Non-Goals

**Goals:**

- 用一个控件暴露服务端已有的集合过滤，且不破坏"地址即状态"的既有约定。
- 让"勾了却看到空页"这种情况自带解释，而不是让人怀疑页面坏了。
- 改动集中在 `buildListQuery` 与列表视图，不动详情链路与数据层。

**Non-Goals:**

- 不在前端重新推导集合范围，也不为"是否有差异"新增任何本地判定。
- 不改结果列文案、编号、进入详情规则。
- 不改 `showTotal` 文案（总数已经等于集合条数，再改措辞属于额外咀嚼）。
- 不处理 `核查失败` 是否属于该集合。

## Decisions

**1. 参数只在勾选时发 `scope=warn`，不勾选时不发。**

与 `matched` 的既有写法一致（缺省即不写），地址干净、请求与地址一一对应。备选是永远发 `scope=all`：与后端默认等价，但会让每条地址都多一个无信息量的键，也让"缺省不写回"的规范化规则出现例外。

**2. 用复选框承载这句 10 字文案，不用开关组件，也不做匹配态下拉的第 5 项。**

antd 的开关文案惯例在 4 字以内，10 字放上去会被截断或挤成两行；复选框天然容纳句子式标签，视觉上仍是"勾一个筛选"。做成下拉第 5 项被否：它把两个正交维度压成一个键，直接丢掉"集合内只看未匹配"这个真实组合。

**3. 集合以服务端为唯一真相，前端不做任何二次推导。**

页面上「疑似未审」的本地判定里含"参考侧缺失"这一支（`src/diff/records.js`），而服务端 `warn` 只认"未匹配"或"匹配且有差异记录"。两者在异常数据上可能不一致。选择让服务端说了算，而不是在勾选时再补一次本地过滤——后者需要第二次请求再合并分页，正是后端已经否掉的方案。代价是承认控件文案是描述性的，这条已写进规格。

**4. `warn × 未知` 保留组合、只做定向空态文案，不置灰、不自动重置。**

- 不自动重置：会静默改掉使用者刚设的匹配态，且与"地址即状态"冲突。
- 不置灰「未知」选项：当地址直开就带着这个组合时，会出现"置灰又被选中"的矛盾呈现，为省一次点击引入一个更怪的态，不划算。
- 定向文案是必须项：既有规格已要求空态保留控件可用，这里只是把文案从"没有符合条件的结论"细化为"『未知』匹配态下不存在疑似未审或有差异的结论"。

**5. `scope` 并入现有 `state` computed 与 `toListQuery`，并同步扩充规范化 watch 的比对键列表。**

新键只接受 `warn`，其余一律视为未勾选，与 `matched` 的白名单校验同风格。规范化 watch 的键数组必须同时加上 `scope`，否则地址里的 `scope` 既不会被纠正也不会被保留。

**6. 不新增组件、不新增依赖、不新增 API 模块导出。**

`buildListQuery` 加一个字段即可；空态继续走现有的 `emptyDescription` 单一 computed，按"加载中 → 取数失败 → 无交集 → 真的没有"的优先级返回文案，避免模板里堆四份分支。

## Risks / Trade-offs

- **控件文案与后端集合未来漂移** → 后端把 `核查失败` 纳入 `warn` 时，文案会变成"只说对三分之二"。缓解：在 `tasks.md` 记一条待办，后端扩展取值时同步改文案与本规格。
- **参考侧缺失但 `matched=1` 的条目显示为「疑似未审」却不在集合内** → 已由规格声明"以服务端为准"；若实际数据出现该情况，属后端谓词对齐问题，不在前端修补。
- **规范化 watch 漏加 `scope`** → 地址不会被纠正，分享后勾选状态可能丢失。缓解：任务中显式点名该处，并在本地手动核对"勾选 → 刷新 → 仍在勾选"。
- **空态文案分支增多导致误判** → 保留单一 computed 的优先级顺序，勾选 + 未知组合不得落入"真的没有"分支。
- **查询串回归** → `buildListQuery` 已有一组用例如 `matched` 缺省不发；新增 `scope` 用例必须同时锁住"未勾选不带键"，否则容易变成永远发 `scope=all`。

## Migration Plan

纯前端读侧参数，无数据迁移。上线即生效；回滚为移除勾选项与 `scope` 透传，服务端不受影响（不传该参数即为 `all`）。

## Open Questions

- 后端何时把 `核查失败` 纳入 `warn`：不阻塞本次，纳入时需同步修订控件文案与本规格，届时再评估是否改名为「仅看疑似未审、差异或核查失败」。
